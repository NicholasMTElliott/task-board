### Migration Tooling
- Flyway via Docker (`redgate/flyway`) for SQL-first schema migrations
- Scripts in `db/migrations`, applied via `scripts/migrate.ps1`
- Migration chain: V1 (processed_events) → V2 (pgmq_core) → V3 (events_queue) → V4 (card_state) → V5 (run_log) → V6 (run_log step_name) → V7 (pgmq_pings_queue) → V8 (card_state_claimed_at) → V9 (agent_run) → V10 (step_result) → V11 (drop_run_log) → V12 (metrics: estimate column, started_at indexes, SQL views) → V13 (session timing: session_startup_ms on agent_run, session_exec_ms on step_result) → V14 (failure_reason: failure_reason TEXT NULL + CHECK constraint on agent_run; v_run_metrics updated to use failure_reason = 'RATE_LIMIT') → V15 (multi-tenant: drop & recreate `agent_run`, `step_result`, `card_state`, `processed_events` with `tenant_id` as leading PK column, all indexes lead with `tenant_id`, no data preserved) → V16 (recreate `v_run_metrics`, `v_step_duration`, `v_card_metrics`, `v_card_rework` projecting `tenant_id`) → V17 (candidate-group columns on `step_result`: `provider NOT NULL` backfilled, `candidate_group_id UUID NULL`, `candidate_index INT NULL`, `selected BOOL NULL`, `quality_score NUMERIC(4,2) NULL`, `evaluator_reasoning TEXT NULL`, partial index on `(tenant_id, candidate_group_id) WHERE candidate_group_id IS NOT NULL`, paired CHECK constraint on `(candidate_group_id, candidate_index)`) → V18 (recreate `v_step_duration` with candidate columns; new `v_candidate_outcomes` and `v_provider_role_metrics` views aggregated by `(role, provider)`) → V19 (partial UNIQUE index `uq_step_result_candidate_slot ON (tenant_id, candidate_group_id, candidate_index) WHERE candidate_group_id IS NOT NULL` so a duplicate-candidate-row bug fails loudly at the DB instead of producing silently-wrong metrics)

- ✅ `--mode init` + bundled templates (`InitRunner`, `templates/from-scratch-{claude,codex,opencode}/`): scaffolds a fresh `./.aiboard/` from a bundled template. Templates ship next to `aiboard.exe` via `<Content Include="..\..\..\templates\**\*" />`. All three produce the **KvA shape** (single `Ready` column + `Activity` field + `assignee isEmpty` lock) with a single agent per step, but with different role.provider/role.model tiers: claude→docker-claude-cli (opus/sonnet/haiku), codex→codex (gpt-5.5/5.4/5.4-mini/5.3-codex with state-level `fullAuto+sandbox=read-only` providerParams), opencode→docker-opencode (qwen3.6-think for design/QA/review/specialist, no-think for impl/gates/board_analyst). **Substitution**: `__OWNER__` / `__OWNER_SLASH_REPO__` / `__PROJECT_NUMBER__` replaced from CLI flags / env / prompts. Auto-detect via `gh repo view --json owner,name` when interactive (best-effort; gh missing or unauthed silently falls through to prompt). **Force semantics**: `--force` overwrites an existing `./.aiboard/` but preserves operator-added files (e.g. `appsettings.user.json` for local secrets) — only files present in the template are re-written. **Bare-flag normalisation**: `CliDefinitions.NormalizeBareBooleanFlags` rewrites bare `--force` / `--non-interactive` to `--name=true` so `AddCommandLine`'s SwitchMappings bind them. **Early bail-out**: dispatch runs immediately after the unknown-flag scan, BEFORE `WorkflowConfig` registration / provider probing / DB connection — init has no need for any of those services and must succeed in a project with no `.aiboard/`, no Docker, no Postgres. **Test seam**: `InitRunner` constructor accepts `TextReader stdin`, `TextWriter stdout`, `Func<string> getCwd`, `Func<string> getExeDir`, `ExternalCommandDelegate runExternal` (all optional; defaults wire to real Console / Directory / Process). 13 tests cover happy path, missing values, unknown template, idempotency guard, `--force` overwrites template files but preserves operator additions, gh-detect stub, prompt fallback on gh failure, env-var path, repo-without-slash auto-expansion, and a real-templates JSON-validity smoke test that pins template authoring against syntax breaks.

- ✅ `--mode scaffold-board --board-id N [--apply]` (`ScaffoldBoardRunner` + `BoardScaffoldDiff` + `IBoardShapeApplier` / `GitHubProjectShapeApplier` / `NullBoardShapeApplier`): dry-run-by-default board provisioner. Pure `BoardScaffoldDiff.Compute(WorkflowConfig, BoardShape) → BoardScaffoldPlan` walks **every requirement source** (filters with `equals`/`notEquals` operators, transition actions `setField`/`clearField`/`updateParentSum`/`moveToColumn`/`addLabel`/`removeLabel`, polling priority field+order, estimation field+scale, cardTypeField+type names, cardTypes labels via `labelPrefix`) and diffs against the introspected shape. `addLabel` and `removeLabel` are symmetric — both reference a label that must exist in the repo so `gh issue edit --remove-label` doesn't fail on unknown labels. Plan groups results into **CREATE actions** (missing fields → `gh project field-create --data-type SINGLE_SELECT`; missing labels → `gh label create --repo`) and **WARN actions** (existing field needs new options; Status column missing) — the latter handled manually since GHv2 GraphQL surface for option mutation is brittle and the GitHub UI takes one click. Default mode prints plan + exits 0; `--apply` re-runs the same path and executes CREATE actions. **Idempotency**: applier matches stderr against `"already exists"` / `"name has already been taken"` and returns `ApplyOutcome.AlreadyExists` (success, marker `=`). Bare `"validation failed"` is intentionally NOT matched — that would silently swallow real failures (invalid name, bad option, missing flag). **Comma-in-option guard**: `gh --single-select-options` is comma-separated; option names containing `,` are rejected locally before shelling out. **Process-startup robustness**: gh missing from PATH (Win32Exception/FileNotFoundException) and other process-startup failures are caught by the applier and surfaced as `ApplyResult.Failed` instead of unhandled exceptions; `OperationCanceledException` propagates so callers can stop apply runs cleanly. **Test seam**: `GitHubProjectShapeApplier` constructor accepts optional `ProcessRunner` delegate. **Provider-vs-applier registration mirrors probe pattern**: github registers `GitHubProjectShapeApplier`; `TryAdd<NullBoardShapeApplier>` covers stub/Trello (runner exits 1 when `--apply` is requested against a `CanApply=false` applier). 33 tests across 3 files: 11 in `BoardScaffoldDiffTests` (every requirement source incl. addLabel/removeLabel symmetry, template-value skip, empty-column-list noise suppression, plan flag predicates), 10 in `ScaffoldBoardRunnerTests` (dry-run vs apply, already-exists outcomes, failure exit, manual-only hint, probe-null/probe-throw, no-applier), 12 in `GitHubProjectShapeApplierTests` (gh args shape, comma-option local rejection, already-exists classification, owner-not-configured, bare-repo expansion, label-dup, **regression guards: bare "validation failed" must NOT match, gh-missing throws → Failed, OperationCanceled propagates**).
- ✅ `--mode diagnose --card-id N` (`DiagnoseRunner`): read-only "why isn't this card being picked up?" triage. Fetches the card, prints header (id/title/column/assignees/labels/non-empty fields), then either resolves the state via `WorkflowConfig.ResolveState` and describes the gateType (ELIGIBLE / HOLDING / DONE / ENTRY / IN PROGRESS / manual gate / ambiguous), or — when no state's filters all pass — walks each candidate state's filter chain. **Filter walk** ordered assignee→field→label per state (operator-pitfall frequency); the first failure per state is shown in the per-state listing, then a single "Most likely cause" headline picks the highest-priority failure across all states. **Routing uses structured `FilterFailure(CardFilter Filter, string Description)` records** matched on `Filter.Type` and `Filter.Operator`, never substring-match against the description text — that brittle coupling cost an afternoon in v0.0.21. **Headline branch**: when an `assignee isEmpty` filter fails AND the card has assignees, the runner prints the exact `gh issue edit N --remove-assignee @user` command; this is the most-asked operator pitfall (assignment is the WIP lock and is invisible). **Field-mismatch branch**: surfaces actual-vs-expected per state ("field Activity = 'Design' ✗ is (unset)"). **Label-mismatch branch**: similar with the missing label name. Returns 0 on successful diagnosis (regardless of pickup-eligibility), 1 only on board-fetch failure. 14 tests pin every output path including the headline assigned-card case, the cross-cutting "assigned card with wrong Activity routes to assignee headline" regression guard for the structured-routing refactor, ambiguous resolution, unknown column, and header rendering with non-empty fields.
- ✅ Pre-flight config validation (`StartupConfigValidator`) — **strict-by-default**: every finding is an Error that aborts startup. No Warning category remains; no opt-out flag. Runs after config merge, before tenant resolution, via a temporary pre-host logger. **Rationale**: the prior Warning tier was getting lost in polling-mode startup logs (a ticket gets picked up immediately and the warning scrolls away), so silently misconfigured operators ran for hours/days against half-applied settings. The KvA v0.0.21 case that triggered the change: `Docker.ImageName: aiboard-agent-sandbox:godot` set as a deprecated legacy section, warning issued, missed; the legacy section ONLY binds to `DockerClaudeAgentOptions`, so docker-opencode and docker-claude-qwen candidates ran with the default image despite the operator's clear intent. **Errors enforced**: unknown `BoardProvider`; `BoardProvider=github` missing any of Owner/Repo/ProjectNumber (all listed at once); `BoardProvider=trello` missing any of ApiKey/ApiToken/BoardId; `GitHubProjects` populated but provider≠github (was Warning); `Trello` populated but provider≠trello (was Warning); both `GitHubProjects` AND `Trello` sections populated (was Warning); unrecognized `AgentExecutor` value (was Warning — was silently falling back to auto-detect); legacy `Docker` config section populated (was Warning — error message now explicitly notes that the legacy section ONLY affects docker-claude-cli and that docker-opencode / docker-claude-qwen need their own `DockerAgents:OpenCode` / `DockerAgents:ClaudeQwen` sections); `CodexCli:MaxBudgetUsd` set (was Warning — Codex CLI has no budget flag, value would be silently ignored). Chose NOT to flag missing `WorktreeBasePath`/`PollIntervalSeconds`/`ClaudeCli:ExecutablePath`/stub `Stub:TenantName` (all have sensible defaults). `TenantIdentifierFactory.Create` widened to list all missing keys in one exception instead of first-missing. The legacy `Docker` section binding in `Program.cs` is unchanged — the validator fails before binding takes effect, so operators always see a clear migration error rather than silently-honoured legacy values. Concrete pain case: KvA card #3 v0.0.20 — every implement-step candidate produced real committed work (3 of 5 worktrees on disk had `git diff mainline..HEAD` with 200–330 line diffs across 8–10 files: Cinzel-Medium.ttf added, three TitlePage PNGs deleted, main_menu.gd / test_runner.gd modified) but the evaluator received empty diffs and concluded "all candidates produced no changes; task must be re-run." **Pre-fix root cause**: `GetDiffSummaryAsync` ran `git diff HEAD`, which only catches uncommitted working-tree changes. That's correct for the single-agent / pre-`HandleGitBehaviorAsync` flow (gate-check on canonical sees the agent's uncommitted writes), but wrong for two candidate-evaluation flows: (1) **Per-candidate diff in evaluator's prompt**: `CandidateExecutor.ExecuteSingleCandidateAsync` calls `gitWorkspaceManager.CommitAsync(candidateWorktreePath, ...)` immediately after the agent run, so by the time `BuildEvaluatorTaskPromptAsync` calls `GetDiffSummaryAsync(e.WorktreePath, ...)` HEAD is the commit — working tree is clean — `git diff HEAD` returns empty. (2) **Gate-check diff after candidate-group promotion**: `git reset --hard {winner-branch}` on canonical advances HEAD AND resets the working tree to match HEAD; subsequent gate check's `git diff HEAD` on canonical returns empty even though the winner's committed work is sitting right there in the index. **Fix**: `GetDiffSummaryAsync` accepts optional `string? baseRef` (default null = preserve `git diff HEAD` semantics for back-compat); when set, runs `git diff {baseRef}` which captures both committed-since-base AND uncommitted-since-HEAD changes. Different consumers, different stable base refs: **CandidateExecutor** captures `slotStartCanonicalSha` alongside `canonicalBranch` at slot start (canonical worktree's HEAD SHA before candidates spawn), plumbs it through `RunEvaluatorAsync` → `BuildEvaluatorTaskPromptAsync`, passes to per-candidate `GetDiffSummaryAsync` calls. **AgentRunner** captures `runStartCanonicalSha` after the optional merge step but before the step loop, plumbs it through `RunGateCheckAsync` to its `GetDiffSummaryAsync` call. The two SHAs differ on purpose: per-candidate diff shows only that slot's work (excludes prior promoted slots in multi-step states); gate check shows the run's cumulative work (includes any in-run promotions). On SHA-capture failure the parameter falls back to null → `git diff HEAD` → identical to pre-fix behaviour, so the failure mode is "regression, not crash." Docs intent: relative symlink visibility through Docker bind mount is unaffected (mounting and diff base are orthogonal). Pinned by 7 tests across three layers: **(a) API level** — 5 unit tests in new `GitWorkspaceManagerDiffTests` (default-HEAD-empty-after-commit baseline; explicit-baseRef-shows-committed-work; explicit-baseRef-after-reset-hard-still-shows-work — direct simulation of post-promotion canonical state; explicit-baseRef-includes-uncommitted-changes-too — regression guard for single-agent path's mixed committed+uncommitted shape; GetCurrentSha-returns-stable-hex-sha). **(b) CandidateExecutor integration** — 1 test in `CandidateExecutorEvaluatorPromptTests` (`CommitMode_EvaluatorPromptContainsEachCandidateDiff_NotEmpty` with two candidates writing distinct tracked files outside the gitignored `.aiboard/` directory; asserts both filenames AND content markers appear in the captured evaluator prompt's `\`\`\`diff` blocks — would fail with empty diff sections under the pre-fix behaviour. Also asserts **per-candidate partitioning**: candidate 0's section contains ONLY its own marker, candidate 1's section ONLY its own — guards against a regression that diffs every candidate against the wrong base and leaks the other's content into both sections; section boundaries detected by slicing at `### Candidate {N}` headings and the trailing `## Response Contract` block). **(c) AgentRunner gate-check integration** — 1 test in `AgentRunnerGateCheckTests` (`GateCheck_CommitStage_SeesDiff_WhenHEADAdvancedDuringStep`) that mimics the candidate-flow shape WITHOUT spinning up a real candidate group: the substitute agent does what an orchestrator-plus-promotion would do (writes a tracked file, runs `git add` + `git commit` on the canonical worktree itself, leaving HEAD ahead of `runStartCanonicalSha` by one commit and the working tree clean). Asserts the gate executor's TaskPrompt's `{Diff}` slot still contains the committed file's name and content. Pre-fix this fails with an empty diff because the working tree matched HEAD post-commit — exactly the v0.0.20 KvA card #3 failure shape, just driven by the test agent instead of CandidateExecutor's promotion phase so we don't pay the cost of a full candidate group fixture. The orchestrator-side `git add . && git commit` (line 756 in `ExecuteSingleCandidateAsync`) is unchanged; the diff lookup is the only thing that changed. Documented in `memory-bank/systemPatterns.md` `CandidateExecutor` row.
- ✅ Re-run fast-path for previously-completed steps (`RerunPreambleBuilder`). Motivation: when a card returns from a Questions column for a re-run, every step in the state would re-execute by default — including ones that completed successfully on the first pass. For multi-step states (`Ready for Design` has 4 steps; impl 2; test 2), that wastes minutes and tokens on cycles that have nothing new to add. Concrete pain case: KvA card #3's `review_related_tickets` (Haiku via `board_analyst`) running fully on every re-run after `create_design` returned NEEDS_INFO. **Mechanism**: per agent invocation (regular step / candidate group / gate check / optional specialist reviewer / evaluator), call `RerunPreambleBuilder.TryBuildPreambleAsync` BEFORE the call. Two signals must both hold for the preamble to be injected: (a) the step's marker is present in the card's existing comments, AND (b) the most recent `step_result` row for `(card, state, step)` from a run other than the current one has `outcome = COMPLETE`. When both true, prepend a "RE-RUN; bail with COMPLETE if nothing relevant changed" preamble that embeds the prior comment body and instructs the agent to confirm OR refresh. **Operator force-rerun lever**: delete the step's comment from the card before moving back to Ready → marker absent → preamble suppressed → step runs fresh. **No config knobs.** Two preamble variants share identical detection: `PreambleVariant.TaskPrompt` ("if your prior output remains accurate, respond COMPLETE") for single-agent and per-candidate prompts; `PreambleVariant.Evaluator` ("if all candidates confirmed prior, pick any with winner_index 0") for the evaluator's prompt. **Step-name matcher** accepts three shapes for DB lookups so the same canonical step name finds prior rows whether the prior run was single-agent, single-slot candidate, or multi-slot candidate: exact (`step.Name`), single-slot evaluator (`step.Name:evaluator`), multi-slot evaluator (`step.Name:slot-N:evaluator`). NEEDS_INFO and ERROR prior outcomes don't qualify — only COMPLETE does (so the step that asked the questions still re-runs fully with the answers in scope). The current run's own rows are excluded by run-id filter so prior steps in the same run don't accidentally trigger fast-paths for later steps. **Injection sites**: AgentRunner regular step (line 418, covers single-agent and candidate-group paths because both consume the same `resolvedPrompt`), AgentRunner gate check (after `gatePromptTemplate` builds), AgentRunner optional specialist reviewer (inside `ExecuteOptionalStepsAsync` per step), CandidateExecutor evaluator (inside `BuildEvaluatorTaskPromptAsync`, prepended before the existing `## Original Step Task` block). The candidate-side injection at the regular-step site flows through `groupRequest.TaskPrompt` to all candidates in all slots — slot 0 winners and slot 1 fallbacks alike see the same preamble. **`CandidateGroupRequest.ExistingComments`** (new optional field) threads the card's comments through to the evaluator without an extra board fetch (AgentRunner already has the list in scope at the call site). **Constructor injection is nullable-optional** on both `AgentRunner` and `CandidateExecutor` so unit tests that omit the dependency just get null preambles (existing behavior preserved). Production DI registers `RerunPreambleBuilder` as a singleton in `Program.cs` next to `CandidateExecutor`. Zero schema changes, zero new validator rules, zero workflow JSON edits required. Pinned by 14 unit tests in `RerunPreambleBuilderTests` (marker absent, marker without DB record, COMPLETE / NEEDS_INFO / ERROR outcomes, empty-after-strip, current-run exclusion, multi-slot evaluator suffix, single-slot evaluator suffix, both variants, duplicate-marker last-wins, marker-not-at-start-of-body) plus 2 integration tests in `CandidateExecutorEvaluatorPromptTests` (full evaluator preamble injection through CandidateExecutor; marker absent suppresses preamble even when DB has prior COMPLETE).
