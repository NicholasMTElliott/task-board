### Migration Tooling
- Flyway via Docker (`redgate/flyway`) for SQL-first schema migrations
- Scripts in `db/migrations`, applied via `scripts/migrate.ps1`
- Migration chain: V1 (processed_events) → V2 (pgmq_core) → V3 (events_queue) → V4 (card_state) → V5 (run_log) → V6 (run_log step_name) → V7 (pgmq_pings_queue) → V8 (card_state_claimed_at) → V9 (agent_run) → V10 (step_result) → V11 (drop_run_log) → V12 (metrics: estimate column, started_at indexes, SQL views) → V13 (session timing: session_startup_ms on agent_run, session_exec_ms on step_result) → V14 (failure_reason: failure_reason TEXT NULL + CHECK constraint on agent_run; v_run_metrics updated to use failure_reason = 'RATE_LIMIT') → V15 (multi-tenant: drop & recreate `agent_run`, `step_result`, `card_state`, `processed_events` with `tenant_id` as leading PK column, all indexes lead with `tenant_id`, no data preserved) → V16 (recreate `v_run_metrics`, `v_step_duration`, `v_card_metrics`, `v_card_rework` projecting `tenant_id`) → V17 (candidate-group columns on `step_result`: `provider NOT NULL` backfilled, `candidate_group_id UUID NULL`, `candidate_index INT NULL`, `selected BOOL NULL`, `quality_score NUMERIC(4,2) NULL`, `evaluator_reasoning TEXT NULL`, partial index on `(tenant_id, candidate_group_id) WHERE candidate_group_id IS NOT NULL`, paired CHECK constraint on `(candidate_group_id, candidate_index)`) → V18 (recreate `v_step_duration` with candidate columns; new `v_candidate_outcomes` and `v_provider_role_metrics` views aggregated by `(role, provider)`) → V19 (partial UNIQUE index `uq_step_result_candidate_slot ON (tenant_id, candidate_group_id, candidate_index) WHERE candidate_group_id IS NOT NULL` so a duplicate-candidate-row bug fails loudly at the DB instead of producing silently-wrong metrics)

- ✅ Multi-agent candidate evaluation (`CandidateExecutor`, opt-in per step). `WorkflowStep` extended with `Candidates` (list of `CandidateOverride { Provider, Model?, ProviderParams? }`) + `Evaluator` (`EvaluatorConfig { Role, TaskPrompt(File)?, Scoring }` with `EvaluatorScoring.WinnerWithScores | WinnerOnly`). When set, the runtime spawns N candidate worktrees off canonical HEAD, runs each provider in parallel, then invokes the evaluator role to pick a `winner_index` + 0–10 `scores`. Winner is promoted via `git reset --hard`; losers are torn down. Per-(role, provider) wins/scores/duration recorded in V17-widened `step_result` (new columns: `provider NOT NULL` backfilled to `claude-cli`, `candidate_group_id UUID NULL`, `candidate_index INT NULL`, `selected BOOL NULL`, `quality_score NUMERIC(4,2) NULL`, `evaluator_reasoning TEXT NULL` + paired CHECK constraint). V18 recreates `v_step_duration` with the new columns and adds `v_candidate_outcomes` + `v_provider_role_metrics` (aggregated wins/win_rate/avg_score/avg_duration by `(role, provider)`). `IMetricsStore.GetProviderRoleMetricsAsync` and `GetCandidateHeadToHeadAsync` (alphabetical-pair self-join, ties counted as "neither selected") feed two new MetricsRunner output sections (suppressed when no candidate data exists yet) and two Grafana bargauge panels. Validator (`WorkflowConfigValidator.Validate`) errors on: `candidates` without `evaluator` (and vice versa), duplicate provider per group, more than 4 candidates per step, candidates on a `discard` state (winner promotion needs git commits), evaluator role missing from `Roles`, evaluator with neither `taskPrompt` nor `taskPromptFile`. Verdict parser (`CandidateExecutor.ParseEvaluatorVerdict`) accepts JSON in three shapes — fenced `\`\`\`json`, whole-document, last balanced `{...}` with `winner_index` — and rejects out-of-range or negative `winner_index` rather than promoting nothing. **Score sanitisation:** the parser drops scores outside `[0, 10]` to null (keeps reasoning) so out-of-contract values don't pollute `avg_quality_score` in metrics; **dedupes duplicate `index` entries** in `scores[]` with last-write-wins semantics so a draft+revise output doesn't double-count. **All-failed merged outcome** prefers `NEEDS_INFO` over `ERROR`: when every candidate returns non-COMPLETE, the step's surfaced outcome is `NEEDS_INFO` if any candidate asked a question (recoverable — card moves to Questions for human answer), otherwise `ERROR`. Candidate declaration order does NOT determine routing. **Phases 3–5 wrapped in `try/finally`**: verdict parsing, persistence, winner promotion, and per-candidate comment posting run inside a finally block that always deletes the evaluator's inline-system-prompt temp file (`$TMP/aiboard-evaluator-{guid}.md`), so unexpected exceptions in any of those phases don't orphan files in `/tmp`. Evaluator step is recorded as a regular `step_result` row with name suffix `:evaluator`, NOT carrying `candidate_group_id` (so `WHERE candidate_group_id IS NOT NULL` filters in the metrics views never count it as a candidate). Candidate branch naming uses a **separate** `aiboard-cand/{cardId}-{groupShort}-{index}-{provider}` prefix — NOT nested under the canonical branch path — because nested git worktrees fail. Candidates run as short-lived processes (no session reuse — each candidate has a different worktree mount). Default evaluator role in `workflow.github.json` is `evaluator` → `claude-opus-4-6`; system prompt at `prompts/evaluator.md`; per-step-type task prompts at `prompts/evaluator/code_review_candidates.md` + `gate_check_candidates.md`. **V19 partial UNIQUE index** (`uq_step_result_candidate_slot ON (tenant_id, candidate_group_id, candidate_index) WHERE candidate_group_id IS NOT NULL`) is exercised by `PgRunStoreCandidateUniqueIndexTests`, which connects to the local Postgres from `docker-compose.yml` (override via `TASKBOARD_TEST_PG_CONNECTION` env var; test silently skips if the DB is unreachable so other suites still run). The test inserts a candidate row, then attempts a second row with the same `(tenant, group, index)` but a different `step_name` (bypassing the run-id+step-name `ON CONFLICT` clause), and asserts the V19 UNIQUE constraint fires with SQLSTATE `23505`.
- ✅ Claude-CLI-on-Qwen executor (`DockerClaudeQwenAgentExecutor`, provider key `docker-claude-qwen`): third Qwen-target executor sitting alongside `docker-opencode`. Reuses `aiboard-agent-sandbox:latest` (the existing Claude CLI image) — the Qwen redirect is purely runtime env-var work, no separate sandbox image. Same Claude CLI invocation as `DockerClaudeAgentExecutor` (`--json-schema`, NDJSON parsing, exit-code classification, rate-limit detection) with the **headline benefit** that `--json-schema` is enforced server-side: Claude CLI translates the schema to a tool-call definition, the proxy forwards it, llama.cpp's `qwen3_coder` jinja template constrains generation. So structured-output reliability matches the real-Anthropic path (per Qwen-3.6.md's 96.7–100% tool-call benchmark) without the prompt-engineered + retry-loop mechanics OpenCode needs. **Connection setup**: `DockerClaudeQwenMountBuilder` writes a synthetic `~/.claude` (settings.json with `hasCompletedOnboarding=true` + dummy credentials.json) to a per-run temp dir, mounts it RW at `/home/agent/.claude`, and injects `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` as docker `-e` env vars. Critical: must NEVER mount the host's real `~/.claude` (would leak Anthropic credentials into a Qwen-target run); a regression guard test (`BuildAsync_NoHostCredentialDirReferenced_OnlySyntheticClaudeMount`) pins the `aiboard-cq-claude-{guid}` staging-dir naming. **Cache-friendliness toggles**: `DisableAttributionHeader` (sets `CLAUDE_CODE_ATTRIBUTION_HEADER=0`) and `DisableNonessentialTraffic` (sets `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`) both default true, per the Qwen-3.6.md model card — without them, the per-request attribution header changes invalidate llama.cpp's prefix cache and the CLI sends telemetry pings that 404 against the local proxy. **Per-call model selection** via `AgentExecutionContext.Model` → `--model` CLI flag (which wins over `ANTHROPIC_MODEL` env var); fallback to `DockerClaudeQwenAgentOptions.ModelName`. **Provider URL pitfall**: default `ProviderBaseUrl` is bare `http://llama-server:8080` (NO `/v1` suffix), unlike OpenCode's default which DOES include `/v1`, because the Anthropic Messages adapter inside Claude CLI appends `/v1/messages` itself while OpenCode's openai-compatible adapter appends `/chat/completions` to whatever baseURL ends with. Stderr signatures via `CliFailureHintDetector.ClaudeQwenSignatures` (Network / Model / Auth / Config / Schema with Anthropic-style hint texts referring to `ANTHROPIC_*` env vars and `~/.claude/settings.json`). No session reuse implemented (each step spawns a fresh container; fine for the candidate-evaluation use case where worktree mounts differ per candidate anyway). Auto-registered when Docker daemon is detected; fail-fast startup when `AGENT_EXECUTOR=docker-claude-qwen` is explicitly set but Docker is unavailable. `StartupConfigValidator.KnownAgentExecutors` and `AgentExecutorResolver.ForSingleExecutor` both include the new key. The headline reason this exists alongside `docker-opencode` is so the candidate-evaluation feature can A/B them on the same task and accumulate per-(role, provider) win rates — schema-enforced vs. prompt-engineered structure on the same backend, decided by data over time.
- ✅ V18 view-drop fix: `db/migrations/V18__candidate_metrics_views.sql` originally used `CREATE OR REPLACE VIEW v_step_duration` to add the candidate columns (provider/candidate_group_id/candidate_index/selected/quality_score) mid-list, but Postgres rejects column reorders/renames in `CREATE OR REPLACE VIEW` with "cannot change name of view column ...". Fixed by prepending `DROP VIEW IF EXISTS v_step_duration;` so the migration applies cleanly on first run and is idempotent across re-runs. The drop is safe: `v_card_metrics`, `v_run_metrics`, `v_card_rework` all source directly from base tables (`agent_run` / `step_result`), not from `v_step_duration`. The bug was masked locally for a while because failed Flyway runs roll back without leaving a history row, so re-running the migrate step kept silently failing while V19 (which depends on V18 having created the new shape) couldn't apply.
- ✅ OpenCode-in-Docker executor (`DockerOpenCodeAgentExecutor`, provider key `docker-opencode`): mirrors the DockerClaude pattern for the OpenCode CLI against a local OpenAI-compatible llama.cpp server (default `http://llama-server:8080/v1` — the `/v1` suffix is required because the sandbox uses OpenCode's `@ai-sdk/openai-compatible` adapter, which appends `/chat/completions`; on the `llm-net` bridge network owned by the sibling `local-llm` compose project). The sandbox image at `docker/opencode-sandbox/` (node:22-slim + OpenCode CLI + git + ripgrep + gettext) templates `~/.config/opencode/opencode.json` from env vars at container start via `entrypoint.sh` — no secrets baked in. The template registers **both Qwen3.6 virtual models** — `qwen3.6-35b-a3b` (no thinking, fast, ~65 tok/s, for tool-call loops) and `qwen3.6-35b-a3b-think` (thinking, ~7× tokens per turn, for design / synthesis) — both with `limit.context: 131072` matching the server's `--ctx-size`. The active model is parameterised by `OPENCODE_MODEL_NAME`; `small_model` is hardcoded to the `-think` variant per the local-llm/Qwen-3.6.md card recommendation, so OpenCode's auto-compaction summaries get the better-grounded reasoning treatment (preserves file paths and identifiers that the no-think variant tends to drop). `compaction.{auto: true, prune: true}` is enabled. **Per-call model selection**: `DockerOpenCodeMountBuilder.BuildAsync` accepts an optional `modelOverride` parameter; the executor sources it from `AgentExecutionContext.Model` (which comes from the workflow role's `model` field), falling back to `DockerOpenCodeAgentOptions.ModelName` when the role didn't pin one. So an `implementer` role with `"model": "qwen3.6-35b-a3b"` and a `senior_engineer` role with `"model": "qwen3.6-35b-a3b-think"` route to the same llama-server but trigger different inference modes via the proxy's `-think` alias rewrite. The entrypoint **JSON-escapes** the three substituted env vars (`OPENCODE_PROVIDER_BASE_URL`, `OPENCODE_AUTH_TOKEN`, `OPENCODE_MODEL_NAME`) before running `envsubst`, so a token or URL containing `\` or `"` produces valid JSON (control chars `\n`/`\t` etc. are not handled — would surface as malformed JSON, deliberately). `DockerOpenCodeAgentOptions` derives from `DockerAgentOptionsBase` (section key `DockerAgents:OpenCode`; defaults: `NetworkMode=llm-net`, `ContainerNamePrefix=aiboard-oc`, `TimeoutSeconds=600` for cold prefix cache). `DockerOpenCodeMountBuilder` adds only the shared worktree/`.git` mounts (no credential staging — llama.cpp accepts a dummy token passed via env var). Output parsing via `OpenCodeOutputParser` (three strategies: fenced JSON → whole-document → last balanced `{...}` with outcome); bounded retry loop on malformed output (`MaxRetriesOnMalformedOutput` default 2). **Rate-limit detection runs on three paths** to avoid silent misclassification: (1) non-zero exit + matching stderr, (2) exit 0 + empty stdout + matching stderr, (3) exit 0 + non-empty stdout + parse failure + matching stderr. Path 3 was a real bug fixed in review — without it an upstream rate limit that returned "I can't help right now" prose would burn the retry budget and end up classified as a parse failure (`{outcome: ERROR}`) instead of a `RateLimitException` (which restores the card to its trigger column). On final retry exhaustion (no rate-limit signal) the executor returns `{outcome: ERROR}` with raw stdout in detail rather than throwing. Stderr signatures via `CliFailureHintDetector.OpenCodeSignatures` (Network / Config / Model / Auth — oriented at local-server failure modes, e.g. `llm-net not found`, `could not resolve host`, `model not found`). Auto-registered when Docker daemon is detected; fail-fast startup when `AGENT_EXECUTOR=docker-opencode` is explicitly set but Docker is unavailable. `StartupConfigValidator.KnownAgentExecutors` and `AgentExecutorResolver.ForSingleExecutor` both include the new key. Role-suitability guidance (don't route thinking-heavy roles to Qwen with `--reasoning off`) lives in `docs/OpenCodeSandbox.md` — not enforced in code, by design, so the eventual multi-agent candidate-evaluation feature can measure the trade-off instead of hiding it. Shared `CliFailureHintDetector` was extracted from `CodexAgentExecutor` for reuse.
