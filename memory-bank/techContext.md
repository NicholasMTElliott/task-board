### Migration Tooling
- Flyway via Docker (`redgate/flyway`) for SQL-first schema migrations
- Scripts in `db/migrations`, applied via `scripts/migrate.ps1`
- Migration chain: V1 (processed_events) → V2 (pgmq_core) → V3 (events_queue) → V4 (card_state) → V5 (run_log) → V6 (run_log step_name) → V7 (pgmq_pings_queue) → V8 (card_state_claimed_at) → V9 (agent_run) → V10 (step_result) → V11 (drop_run_log) → V12 (metrics: estimate column, started_at indexes, SQL views) → V13 (session timing: session_startup_ms on agent_run, session_exec_ms on step_result) → V14 (failure_reason: failure_reason TEXT NULL + CHECK constraint on agent_run; v_run_metrics updated to use failure_reason = 'RATE_LIMIT') → V15 (multi-tenant: drop & recreate `agent_run`, `step_result`, `card_state`, `processed_events` with `tenant_id` as leading PK column, all indexes lead with `tenant_id`, no data preserved) → V16 (recreate `v_run_metrics`, `v_step_duration`, `v_card_metrics`, `v_card_rework` projecting `tenant_id`) → V17 (candidate-group columns on `step_result`: `provider NOT NULL` backfilled, `candidate_group_id UUID NULL`, `candidate_index INT NULL`, `selected BOOL NULL`, `quality_score NUMERIC(4,2) NULL`, `evaluator_reasoning TEXT NULL`, partial index on `(tenant_id, candidate_group_id) WHERE candidate_group_id IS NOT NULL`, paired CHECK constraint on `(candidate_group_id, candidate_index)`) → V18 (recreate `v_step_duration` with candidate columns; new `v_candidate_outcomes` and `v_provider_role_metrics` views aggregated by `(role, provider)`) → V19 (partial UNIQUE index `uq_step_result_candidate_slot ON (tenant_id, candidate_group_id, candidate_index) WHERE candidate_group_id IS NOT NULL` so a duplicate-candidate-row bug fails loudly at the DB instead of producing silently-wrong metrics)

- ✅ Multi-agent candidate evaluation (`CandidateExecutor`, opt-in per step). `WorkflowStep` extended with `Candidates` (list of `CandidateOverride { Provider, Model?, ProviderParams? }`) + `Evaluator` (`EvaluatorConfig { Role, TaskPrompt(File)?, Scoring }` with `EvaluatorScoring.WinnerWithScores | WinnerOnly`). When set, the runtime spawns N candidate worktrees off canonical HEAD, runs each provider in parallel, then invokes the evaluator role to pick a `winner_index` + 0–10 `scores`. Winner is promoted via `git reset --hard`; losers are torn down. Per-(role, provider) wins/scores/duration recorded in V17-widened `step_result` (new columns: `provider NOT NULL` backfilled to `claude-cli`, `candidate_group_id UUID NULL`, `candidate_index INT NULL`, `selected BOOL NULL`, `quality_score NUMERIC(4,2) NULL`, `evaluator_reasoning TEXT NULL` + paired CHECK constraint). V18 recreates `v_step_duration` with the new columns and adds `v_candidate_outcomes` + `v_provider_role_metrics` (aggregated wins/win_rate/avg_score/avg_duration by `(role, provider)`). `IMetricsStore.GetProviderRoleMetricsAsync` and `GetCandidateHeadToHeadAsync` (alphabetical-pair self-join, ties counted as "neither selected") feed two new MetricsRunner output sections (suppressed when no candidate data exists yet) and two Grafana bargauge panels. Validator (`WorkflowConfigValidator.Validate`) errors on: `candidates` without `evaluator` (and vice versa), empty provider on a candidate, evaluator role missing from `Roles`, evaluator with neither `taskPrompt` nor `taskPromptFile`. **Previously rejected, now allowed** (the rejections were over-conservative): unlimited candidate count (was capped at 4 — eval-prompt size is the user's call), duplicate providers per group (legitimate for same-provider model A/B like Opus vs Sonnet on Claude, also for variance-measurement runs), `gitBehavior: discard` (now supported via file-based winner promotion). Verdict parser (`CandidateExecutor.ParseEvaluatorVerdict`) accepts JSON in three shapes — fenced `\`\`\`json`, whole-document, last balanced `{...}` with `winner_index` — and rejects out-of-range or negative `winner_index` rather than promoting nothing. **Score sanitisation:** the parser drops scores outside `[0, 10]` to null (keeps reasoning) so out-of-contract values don't pollute `avg_quality_score` in metrics; **dedupes duplicate `index` entries** in `scores[]` with last-write-wins semantics so a draft+revise output doesn't double-count. **All-failed merged outcome** prefers `NEEDS_INFO` over `ERROR`: when every candidate returns non-COMPLETE, the step's surfaced outcome is `NEEDS_INFO` if any candidate asked a question (recoverable — card moves to Questions for human answer), otherwise `ERROR`. Candidate declaration order does NOT determine routing. **Phases 3–5 wrapped in `try/finally`**: verdict parsing, persistence, winner promotion, and per-candidate comment posting run inside a finally block that always deletes the evaluator's inline-system-prompt temp file (`$TMP/aiboard-evaluator-{guid}.md`), so unexpected exceptions in any of those phases don't orphan files in `/tmp`. Evaluator step is recorded as a regular `step_result` row with name suffix `:evaluator`, NOT carrying `candidate_group_id` (so `WHERE candidate_group_id IS NOT NULL` filters in the metrics views never count it as a candidate). Candidate branch naming uses a **separate** `aiboard-cand/{cardId}-{groupShort}-{index}-{provider}` prefix — NOT nested under the canonical branch path — because nested git worktrees fail. Candidates run as short-lived processes (no session reuse — each candidate has a different worktree mount). Default evaluator role in `workflow.github.json` is `evaluator` → `claude-opus-4-6`; system prompt at `prompts/evaluator.md`; per-step-type task prompts at `prompts/evaluator/code_review_candidates.md` + `gate_check_candidates.md`. **V19 partial UNIQUE index** (`uq_step_result_candidate_slot ON (tenant_id, candidate_group_id, candidate_index) WHERE candidate_group_id IS NOT NULL`) is exercised by `PgRunStoreCandidateUniqueIndexTests`, which connects to the local Postgres from `docker-compose.yml` (override via `TASKBOARD_TEST_PG_CONNECTION` env var; test silently skips if the DB is unreachable so other suites still run). The test inserts a candidate row, then attempts a second row with the same `(tenant, group, index)` but a different `step_name` (bypassing the run-id+step-name `ON CONFLICT` clause), and asserts the V19 UNIQUE constraint fires with SQLSTATE `23505`.
- ✅ Discard-mode candidate evaluation: `CandidateExecutor` now supports `gitBehavior: discard` states (design, tasking) by switching the winner-promotion mechanism from `git reset --hard {winner-branch}` (commit modes) to file copy. `PromoteDiscardWinnerArtifacts(winnerWorktree, canonicalWorktree)` clears the canonical's `.aiboard/{tasks,updates}/` then copies the winner's contents in (mirror semantics — a winner that *removed* a file is reflected). All candidate branches (winner included) are torn down afterward; canonical's git state is unchanged. The evaluator prompt also forks: commit modes get `git diff` per candidate (the actual code change); discard modes get the candidate's `.aiboard/tasks/{cardId}.md` content (the design / card body) + listing of `.aiboard/updates/*.md` files (since `.aiboard/` is gitignored, `git diff` is empty for discard candidates and would give the evaluator nothing to compare on). `IsDiscardMode(string?)` is the case-insensitive helper that gates both branches. `comments/` and `images/` are deliberately NOT promoted because they're inputs (refreshed from the board before each run); copying stale candidate copies over canonical inputs would be wrong. Validator no longer rejects candidates on `discard` states; candidate count is uncapped (was 4); duplicate-provider rejection removed (legitimate use cases: same-provider model A/B like Opus vs Sonnet on Claude, and variance-measurement runs of identical agent twice). Tested by `DiscardMode_WinnerArtifactsCopied_NoGitCommitsOnCanonical` in `CandidateExecutorFlowTests`.
- ✅ Claude-CLI-on-Qwen executor (`DockerClaudeQwenAgentExecutor`, provider key `docker-claude-qwen`): third Qwen-target executor sitting alongside `docker-opencode`. Reuses `aiboard-agent-sandbox:latest` (the existing Claude CLI image) — the Qwen redirect is purely runtime env-var work, no separate sandbox image. - ✅ Evaluator prompt — `NEEDS_INFO` is not automatically a deduction (`prompts/evaluator.md`): the prior rule "Failed candidates can't win" lumped legitimate-question NEEDS_INFO together with ERROR, biasing the evaluator toward candidates that fabricated through ambiguity instead of asking. The replacement principle reads the question first: a *legitimate* NEEDS_INFO (genuinely unclear requirement, undocumented behaviour observed during QA, security implication not addressed) demonstrates good judgment and is rewarded; a *trivial / already-answered / fabricated* NEEDS_INFO is the deduction. NEEDS_INFO candidates are now eligible to win the slot — when one does, the evaluator is instructed to set its own `outcome=NEEDS_INFO` and propagate the legitimate question(s) in `questions` (the orchestrator transitions the card to Questions and surfaces those to the operator). `winner_index` is required for both COMPLETE and NEEDS_INFO outcomes (only `null` for ERROR), with the explanation that NEEDS_INFO doesn't promote work — the operator-answered re-run starts from scratch — but the recorded winner credits the question-asking model in per-(role, provider) win-rate metrics so the routing layer favours, not punishes, models with good judgment. Test pinning is intentionally not added: this is prompt-shape guidance the evaluator reads at runtime, not a code-level invariant. The per-step-type prompts (`code_review_candidates.md`, `gate_check_candidates.md`, `design_candidates.md`) are untouched — they cover rubric (what to compare), the system prompt covers process (how to weigh outcomes).
- ✅ Parallel-by-provider candidate execution. Prior shape was a plain `for` loop with `await` inside `ExecuteSlotAsync` Phase 1 — every candidate ran sequentially regardless of provider, so a slot with 4 candidates across 4 providers paid 4× the wall-clock of a single candidate. Replaced with provider-keyed grouping (`candidates.GroupBy(x => x.Provider, StringComparer.OrdinalIgnoreCase)`) → each group's candidates run sequentially via inner `foreach` → groups run concurrently via `Task.WhenAll`. Wall-clock is now bounded by the slowest provider group (sum of its candidates), not by the sum of all candidates. **Constraint rationale**: same-provider candidates serialize because a single CLI/credential pool plus per-provider rate-limit affinity makes concurrent same-provider invocations a fast route to a 429; different providers run concurrently because they don't contend on each other (codex CLI, docker-claude-cli, docker-opencode, docker-claude-qwen all have independent CLIs and credential pools — and where they share a backend like the local llama-server, the proxy / cache handles concurrency separately). **Index preservation**: candidates retain their declaration-order `index` even when completion is out-of-order, so the evaluator's "Candidate N" enumeration, `step_result.candidate_index`, branch naming `aiboard-cand/...{index}-{provider}`, and `winner_index` semantics are all unchanged. **Error semantics preserved**: `RateLimitException` from any group still propagates through `Task.WhenAll`'s await, AgentRunner still restores the card to the trigger column. Sibling groups that were in-flight at the time of the throw finish their current await before propagation but their results are abandoned — same behavior as today's "candidate 0 throws → candidates 1+ never run" wasted work, just shifted in time. Test recording stores (`RecordingRunStore` in `CandidateExecutorFlowTests` and `CandidateExecutorSlotsTests`) needed lock-guarding because parallel candidates now call `SaveStepResultAsync` concurrently and `List<T>.Add` corrupts internal state from multiple threads. Pinned by `ParallelByProvider_DifferentProvidersOverlap_SameProviderSerializes` in `CandidateExecutorFlowTests`: 3 candidates (claude×2, opencode×1) each sleeping 250 ms; asserts `claude[1].StartedAtUtc >= claude[0].CompletedAtUtc - 10ms` (same-provider serialization with clock-resolution slop) AND `opencode.StartedAtUtc < claude[0].CompletedAtUtc` (cross-provider overlap). The pre-fix sequential shape would fail the second assertion — opencode would only start after both claude calls complete.
- ✅ Per-candidate rate-limit conversion + slot-level / chain-level rate-limit propagation. **Pre-fix problem**: a single candidate hitting `RateLimitException` after exhausting its own retries would propagate the exception out of `Task.WhenAll` in `ExecuteSlotAsync`, abort the entire slot before other candidates' results were collected, skip every remaining slot in the fallback chain, and bubble all the way to `AgentRunner`'s top-level catch — which restored the card to the trigger column and triggered a 30-min poller backoff. So a slot of `[claude (rate-limited), opencode (succeeded)]` would still produce a card-back-to-Ready bounce, and a fallback chain `[primary (rate-limited)] → [fallback]` never reached the fallback. **Fix, three layers**: (1) **per-candidate conversion** in `ExecuteCandidateWithRetriesAsync` returns `(AgentResult, bool RateLimited)` instead of throwing — post-retry `RateLimitException` becomes `AgentResult{ Outcome=ERROR, Detail="[RATE_LIMIT after N attempts] …" }` with the rate-limit flag set; post-retry `TimeoutException` becomes the same shape but with `RateLimited=false` (timeout chains don't trigger card-back-to-Ready, since timeout-only is more often a real problem than a capacity issue). `OperationCanceledException` is intentionally NOT caught — Ctrl+C/shutdown still propagates immediately. (2) **slot-level signal**: `CandidateExecution.RateLimited` carries the per-candidate flag through to the slot. `SlotResult.WasRateLimited` (new field, default false) is set true when `Outcome=Failed` AND every candidate in the slot ended in rate-limit (`executions.All(e => e.RateLimited)`). A single non-rate-limit failure in the slot poisons the flag — meaning the chain isn't purely capacity-blocked. The single-candidate-no-evaluator path also threads the flag for sole-ERROR-from-rate-limit. (3) **chain-level decision** in `AgentRunner.ExecuteAsync`'s slot loop: track `allFailedSlotsWereRateLimited` across the loop. After the loop exits, if the final slot returned `Failed` AND `WasRateLimited=true` AND every prior failed slot was also rate-limited, throw a fresh `RateLimitException` so the existing top-level handler restores the card and the poller backs off. Otherwise just surface `lastSlotResult.AgentResult` normally (ERROR / NEEDS_INFO routes via the workflow's transition map). **Headline outcome**: a slot of `[claude rate-limited, opencode COMPLETE]` now returns Won (qwen wins via the evaluator); a chain of `[primary rate-limited] → [fallback COMPLETE]` now reaches the fallback; only `[primary rate-limited] → [fallback rate-limited]` (or a longer chain of all-rate-limit slots) bubbles up to the existing card-back-to-Ready handler. Existing single-executor (non-candidate) `RateLimitException` propagation is unchanged: those tests in `AgentRunnerRateLimitTests` / `AgentRunnerFailureReasonTests` go through the `else` branch of AgentRunner's per-step path (no slots), and the executor's exception still propagates directly to AgentRunner's catch. Pinned by 4 new tests: `RateLimitException_ExhaustsRetries_SlotReturnsFailedWithRateLimitFlag` and `RateLimitException_NotInRetryOn_SlotReturnsFailedAfterFirstAttempt` (per-candidate conversion + slot flag), `TwoSlot_Slot0AllRateLimited_Slot1Wins_NoExceptionPropagated` (chain fallback works), `SingleSlot_OneCandidateRateLimited_OneSucceeds_SlotWonNotRateLimited` (in-slot mixed outcome). - ✅ Cross-provider agent init file resolver (`AgentInitFileResolver`). **Pre-fix problem**: each CLI agent reads a project-context init file from the working directory at startup — Claude CLI reads `CLAUDE.md`, OpenCode and Codex CLI both read `AGENTS.md`. When a project repo committed only one of those names (e.g. this repo has `CLAUDE.md` only, no `AGENTS.md`), the OTHER providers ran with no project orientation. Falls back to `File.Copy(sibling, expected, overwrite: false)` on `UnauthorizedAccessException` / `IOException` (Windows non-Developer-Mode); copy failures get a Warning so operators see degraded behavior. **Broken-symlink defense**: `File.Exists` returns false for a broken symlink (target doesn't resolve), but `CreateSymbolicLink` would throw on the existing reparse-point stub; the resolver detects `FileInfo.LinkTarget` non-null and `File.Delete`s it before recreating. **Inside vs outside container**: the resolver writes on the host worktree only — the existing host-worktree → `/workspace` bind mount (`DockerMountBuilderBase`) makes the result visible inside Docker containers. Relative symlinks survive the bind mount because both endpoints (`/workspace/CLAUDE.md` and `/workspace/AGENTS.md`) live under the same mount root. No Dockerfile, entrypoint, or mount-builder changes. **Three injection sites** (one line each): `AgentRunner.ExecuteWithSessionAsync` (covers regular step + gate check + optional reviewer — they all flow through the wrapper), `CandidateExecutor.ExecuteSingleCandidateAsync` (per candidate, before retry-loop), `CandidateExecutor.RunEvaluatorAsync` (before evaluator's `ExecuteAsync`). **Opt-out lever**: any pre-existing file at the expected name (committed file, user-managed copy, or empty `touch`-stub) wins because of the existence check. Pinned by 15 unit tests in `AgentInitFileResolverTests` (expected-exists no-op, neither-exists no-op, mirror in both directions across all 5 mapped providers, stub provider no-op, unknown provider no-op, idempotent second call, both-files-distinct preserves user intent, broken-symlink recovery, content-matches-source, **cross-provider sequence (Claude then OpenCode → both files end up correct, regression guard for the multi-step run flow)**, **non-existent workspace doesn't throw — defensive guard for cleanup-race scenarios**) plus 4 integration tests (2 in `AgentRunnerInitFileTests` covering the AgentRunner injection site for both OpenCode-mirrors-Claude and Claude-no-mirror-needed paths; 2 in `CandidateExecutorFlowTests` covering candidate site and evaluator site, both asserting the file existed AT THE MOMENT the executor was called — post-call evaluator promotion may move things). - ✅ Inactivity timer for CLI subprocesses (`InactivityTimeoutException`, `ProcessRunner` monitor). **Pre-fix problem**: `ProcessRunner.RunProcessAsync` had only a single hard wall-clock cap (`TimeoutSeconds`). A stuck OpenCode candidate stuck in an explore-subagent loop with no output for 30 min got the same treatment as a legitimate long implementation streaming NDJSON the whole time — the operator's choice was either a tight cap that killed legitimate runs or a loose cap that wasted 30 min per stuck candidate. Concrete case: KvA card #3 v0.0.20 — `docker-opencode` candidate timed out at 30 min on cold-start explore loop while sibling `docker-claude-qwen` finished the same task in 18 min with steady NDJSON output. **Mechanism**: `ProcessRunner.RunProcessAsync` gains optional `int? inactivityTimeoutSeconds` param. When set, a background monitor task tracks `lastOutputTicks` (updated via `Interlocked.Exchange` in the existing `OutputDataReceived` / `ErrorDataReceived` handlers) and polls every `max(1, min(30, threshold/4))` seconds; if the gap exceeds the threshold while the process is still running, it cancels a scoped CTS that the wait token is linked to. On fire, throws `InactivityTimeoutException : TimeoutException` with the threshold in seconds embedded in the message. Subclassing means: existing `catch (TimeoutException)` blocks in all three Docker executors run their `docker stop -t 30` cleanup paths unchanged; `AgentRunner.ClassifyFailure` maps to `TIMEOUT` failure-reason as before; `CandidateExecutor.ExecuteCandidateWithRetriesAsync`'s retry-on-`TimeoutException` catch covers it transparently — no operator-side `RetryOn` list edits. The hard cap is still the outer bound; null disables inactivity checking. **Defaults bumped**: `DockerAgentOptionsBase.TimeoutSeconds` 900 → 7200 (2h), new `InactivityTimeoutSeconds = 1200` (20m); same for `ClaudeCliLlmOptions` and `CodexCliLlmOptions`. The per-derived `TimeoutSeconds = 600` overrides on `DockerOpenCodeAgentOptions` and `DockerClaudeQwenAgentOptions` were removed so they inherit the new base default. Existing operator overrides (e.g. KvA's `TimeoutSeconds: 1800`) still take precedence — defaults bump only affects fresh installs. **Defensive race-check**: just before firing inactivity, the monitor re-checks `process.HasExited`. The `HasExited` flag updates only when the runtime polls it, so between the top-of-loop check and the threshold comparison the process may have actually exited; without the second check the monitor could fire on a process that completed naturally. The race window is microseconds-to-milliseconds and benign for 20-minute thresholds, but the second check costs nothing and removes the false-positive path. **Test seam**: `ProcessRunnerDelegate` extended with `int? inactivityTimeoutSeconds = null` at end of signature. All 5 CLI executors (`ClaudeAgentExecutor`, `CodexAgentExecutor`, `DockerClaudeAgentExecutor`, `DockerOpenCodeAgentExecutor`, `DockerClaudeQwenAgentExecutor`) pass their option's value through to the runner. Test stubs across `AgentExecutorContractTests`, `CodexAgentExecutorDiagnosticsTests`, `DockerClaudeQwenAgentExecutorDiagnosticsTests`, `DockerOpenCodeAgentExecutorDiagnosticsTests`, `CodexAgentExecutorSchemaCleanupTests`, `CodexParserCorpusTests` updated to take `, _` discard. Pinned by 6 tests: 5 in new `ProcessRunnerInactivityTests` (silent process fires inactivity well before hard cap; fast process exits cleanly; **streaming output keeps process alive — regression guard for the OutputDataReceived → lastOutputTicks update path, since a silent test alone would pass even with a broken handler wiring**; **hard cap shorter than inactivity threshold throws plain `TimeoutException`, not the subclass — pins that `inactivityFired` is not falsely set**; null inactivity → plain `TimeoutException`) and `InactivityTimeoutException_IsRetried_SameAsTimeoutException` in `CandidateExecutorSlotsTests` (subclass falls through retry path). - ✅ Per-candidate diff base ref + gate-check diff base ref (`GitWorkspaceManager.GetDiffSummaryAsync` `baseRef` parameter, `GetCurrentShaAsync` helper). Concrete pain case: KvA card #3 v0.0.20 — every implement-step candidate produced real committed work (3 of 5 worktrees on disk had `git diff mainline..HEAD` with 200–330 line diffs across 8–10 files: Cinzel-Medium.ttf added, three TitlePage PNGs deleted, main_menu.gd / test_runner.gd modified) but the evaluator received empty diffs and concluded "all candidates produced no changes; task must be re-run." **Pre-fix root cause**: `GetDiffSummaryAsync` ran `git diff HEAD`, which only catches uncommitted working-tree changes. That's correct for the single-agent / pre-`HandleGitBehaviorAsync` flow (gate-check on canonical sees the agent's uncommitted writes), but wrong for two candidate-evaluation flows: (1) **Per-candidate diff in evaluator's prompt**: `CandidateExecutor.ExecuteSingleCandidateAsync` calls `gitWorkspaceManager.CommitAsync(candidateWorktreePath, ...)` immediately after the agent run, so by the time `BuildEvaluatorTaskPromptAsync` calls `GetDiffSummaryAsync(e.WorktreePath, ...)` HEAD is the commit — working tree is clean — `git diff HEAD` returns empty. (2) **Gate-check diff after candidate-group promotion**: `git reset --hard {winner-branch}` on canonical advances HEAD AND resets the working tree to match HEAD; subsequent gate check's `git diff HEAD` on canonical returns empty even though the winner's committed work is sitting right there in the index. **Fix**: `GetDiffSummaryAsync` accepts optional `string? baseRef` (default null = preserve `git diff HEAD` semantics for back-compat); when set, runs `git diff {baseRef}` which captures both committed-since-base AND uncommitted-since-HEAD changes. The two SHAs differ on purpose: per-candidate diff shows only that slot's work (excludes prior promoted slots in multi-step states); gate check shows the run's cumulative work (includes any in-run promotions). On SHA-capture failure the parameter falls back to null → `git diff HEAD` → identical to pre-fix behaviour, so the failure mode is "regression, not crash." Docs intent: relative symlink visibility through Docker bind mount is unaffected (mounting and diff base are orthogonal). - ✅ Re-run fast-path for previously-completed steps (`RerunPreambleBuilder`). Motivation: when a card returns from a Questions column for a re-run, every step in the state would re-execute by default — including ones that completed successfully on the first pass.
